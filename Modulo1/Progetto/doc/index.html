1. Descrizione dell'applicazione

Il progetto realizza una scena interattiva in WebGL 1 ispirata all'estetica del cyberspazio di Pokémon: una stanza-griglia stile TRON in cui prende vita Porygon. L'utente assiste all'assemblaggio del modello a partire dai suoi pezzi sparsi sul pavimento, può cambiare modalità di visualizzazione, far eseguire al Pokémon due animazioni di "personalità", e infine evolverlo in Porygon2, modello complesso caricato da file .obj con texture.

L'enfasi del progetto è sulla costruzione gerarchica e procedurale di un modello 3D a partire da poliedri primitivi, sull'animazione articolata a partire da pivot calcolati automaticamente, e sull'integrazione di una pipeline di shader multipli (mesh, solid, texture) coordinati da una macchina a stati.

3. Architettura del codice

Modulo1/Progetto/project/

├── main.js            · runtime (state machine, geometria, render loop)
├── porygon_data.js    · placeholder dati di riferimento

main.js — sezioni

  • Stato globale: enum STATE, VIEW, variabili camera, animazione corrente.
  • Geometria hardcoded: P1_BODY_VERTS/FACES, P1_HEAD_*, P1_EYES_*, P1_FOOT_R/L_*, P1_TAIL_*.
  • Helper mesh: buildPolyhedron (flat normals + edge list per wireframe).
  • Init Porygon1: split colore per faccia, calcolo pivot per gruppo, generazione renderables.
  • Cilindro beam: createAssemblyBeam / drawAssemblyBeam.
  • Animazioni personalità: triggerAnim, computeAnimLocalMatrix, computeAnimWorldExtras.
  • Render loop: render, renderModel, gestione transizioni di stato.
  • UI: setupHUD, setupGUI, label overlay facce.

Programmi GLSL

  • gridProgram — disegno linee colorate uniformi (griglia, beam).
  • colorProgram — geometria solida con luce direzionale e colore uniform.
  • program — geometria con texture 2D + alpha discard (Porygon2 e occhi).

Il programma attivo è scelto in renderModel in funzione di viewMode e della presenza di una texture sul renderable.

4. Macchina a stati e flusso

La scena è governata da un'enum STATE con 6 stati e un'enum VIEW con 3 modalità, entrambe Object.freeze:

STATE: INIT → ASSEMBLING → PORYGON1 → EVOLVE_P1 → EVOLVE_P2 → PORYGON2
VIEW : MESH (default) · SOLID · TEXTURE
  • INIT: i pezzi di Porygon1 sono appoggiati sul pavimento in posizioni deterministiche; il drag del mouse è disabilitato; viewMode iniziale = MESH.
  • ASSEMBLING: avviato da STARTUP. Per ASSEMBLE_DURATION = 3000ms i pezzi vengono interpolati (ease-out cubic) dalla loro startMatrix (traslazione pura) alla targetMatrix = identity. In contemporanea si accende il cilindro di beam attorno al modello.
  • PORYGON1: stato a regime, il modello fluttua (sin(now·0.003)·0.1), accetta drag del mouse e si possono lanciare le animazioni di personalità o l'evoluzione.
  • EVOLVE_P1 / EVOLVE_P2: due fasi di spin attorno all'asse Y (3 giri in 1500ms, poi 2 giri in 1000ms), durante le quali avviene il cambio del modello visualizzato.
  • PORYGON2: viewMode passa automaticamente a TEXTURE e viene mostrato il modello caricato da OBJ.

5. Geometria: Porygon1 costruito a mano

Ogni mesh è definita come due array:

  • Vertici: array di triple [x, y, z] nello spazio modello (già nelle posizioni finali rispetto al centro).
  • Facce: array di triple di indici [i, j, k].

La funzione buildPolyhedron(verts, faces, vertUVs?) genera:

  • Posizioni: 3 vertici per faccia (vertici duplicati) per supportare lo shading flat.
  • Normali: una normale per faccia calcolata via prodotto vettoriale, replicata sui 3 vertici.
  • UV (opzionali): usate solo per gli occhi, dove vengono calcolate con una proiezione planare YZ per cluster (computeEyeUVs) con un padding tale da centrare la "pupilla" all'UV (0.5, 0.5).
  • Line buffer: insieme di edge univoci per il wireframe; gli edge sono normalizzati come min,max per evitare duplicati.

Colorazione per faccia (split & override)

Per ottenere il look canonico di Porygon (corpo rosa, petto/becco/coda/piedi ciano, occhi bianchi con pupilla nera), le mesh del corpo e della testa vengono divise al volo in due gruppi di facce con splitFacesByPredicate: 

headSplit = split(P1_HEAD_FACES, (cx,cy,cz) => cz >= 0.65); // becco
bodySplit = split(P1_BODY_FACES, (cx,cy,cz) => cz >= 0.20 && cy <= -0.05); // petto

Dove l'euristica sbaglia (alcune facce di confine), si applicano correzioni manuali per indice tramite forceFacesToBack(split, faces, [3, 4, 37, 44]). Per individuare gli indici delle facce è disponibile in runtime l'overlay attivabile con il tasto N: ogni faccia mostra un'etichetta (B12, H7, …) proiettata sullo schermo.

Pivot articolari

Per ogni gruppo (head, tail, footR, footL) viene calcolato in fase di init un pivot articolare a partire dalla bounding box dei vertici del gruppo:

  • head → centro X/Z, minY (attacco al corpo)
  • tail → centro X/Y, maxZ (attacco posteriore)
  • footR / footL → centro X/Z, maxY (hip joint)

I pivot sono poi usati come centro di rotazione nelle animazioni di personalità.

6. Pipeline di rendering e shader

Tre programmi GLSL convivono nello stesso file index.html come <script type="x-shader/*"> e sono compilati con webgl-utils.js.

colorProgram (solido con luce)

// fragment
float light = abs(dot(normal, u_reverseLightDirection));
gl_FragColor = u_color;
gl_FragColor.rgb *= (light * 0.7 + 0.3);

L'uso di abs(dot(...)) illumina anche le facce rivolte "controluce" — utile dato che il CULL_FACE è disabilitato per vedere il retro durante assemblaggio/evoluzione.

program (texture + alpha discard)

vec4 texColor = texture2D(u_texture, v_texcoord);
if (texColor.a < 0.1) discard;
gl_FragColor = texColor;
gl_FragColor.rgb *= (light * 0.7 + 0.3);

gridProgram

Vertex shader pass-through e fragment a colore uniforme: serve sia per la griglia della stanza che per il cilindro di beam (linee e anelli).

Depth test: impostato a gl.LEQUAL globalmente, così le facce successive complanari (gli occhi sopra la testa) vincono lo z-fighting essendo disegnate dopo.

7. Animazione di assemblaggio e cilindro di beam

Al click di STARTUP tutti i pezzi del Porygon1 sono posizionati sul pavimento in punti deterministici (vedi groupLayoutXZ). La loro startMatrix è una pura traslazione verso (x, FLOOR_Y − minY, z): questo è cruciale perché l'interpolazione verso l'identità è element-wise sui 16 valori della matrice, e con sola traslazione resta una traslazione lineare (niente shear o scaling spurio durante il volo).

Le parti che appartengono allo stesso gruppo (es. testa + becco + occhi) condividono la stessa startMatrix, così da volare verso il loro target come un unico blocco rigido.

Cilindro di beam

Per coreografare l'assemblaggio si accende un cilindro di raggi bianchi attorno al modello, costruito con gridProgram:

  • 96 raggi verticali sulla circonferenza unitaria, scalati in X/Z dal raggio corrente.
  • Il raggio cresce da 0 a BEAM_MAX_RADIUS = 1.2 con ease-out nei primi 55% della durata, poi resta costante.
  • 6 anelli orizzontali che scorrono lungo l'asse Y in loop su un periodo di 1800ms; il loro alpha sfuma agli estremi per non spezzare la continuità visiva.
  • Tutto il cilindro pulsa leggermente in intensità sincronizzato con now.

8. Animazioni di personalità (atk1 / atk2)

Una volta assemblato, Porygon1 può eseguire due animazioni articolate attivabili da 1 / 2 o dai bottoni del pannello dat.GUI. La struttura è la stessa: 

currentAnim = { kind, startTime, duration };
t    = (now - startTime) / duration;
bell = sin(π · t);   // 0 → 1 → 0 (campana)

A ogni frame, per ogni gruppo articolato si costruisce una matrice di rotazione locale attorno al pivot: M = T(p) · Rx(ax) · Ry(ay) · Rz(az) · T(-p). Questa matrice sostituisce la targetMatrix della parte. Trasformazioni "globali" del modello (saltello, leggera inclinazione) vengono invece applicate al pokeWorldMatrix.

headPitch X · −0.55 · bell (su)Pitch X · +0.45 · bell (giù)
tailPitch X · +0.70 · bellPitch X · −0.55 · bell

Il cleanup di currentAnim avviene una sola volta per frame nel render (non dentro la funzione per-gruppo, per evitare che la prima invocazione azzeri lo stato bloccando le successive).

9. Evoluzione e caricamento di Porygon2 (OBJ)

Al click di EVOLUZIONE!, lo stato passa a EVOLVE_P1: il pokeWorldMatrix viene moltiplicato per uno yRotate proporzionale al tempo per ottenere 3 giri in 1.5s. Subito dopo si entra in EVOLVE_P2 dove la stessa logica vale per Porygon2 (2 giri in 1s). Al termine il viewMode diventa TEXTURE.

Porygon2 è caricato con mesh_utils.js a partire da assets/Porygon2/Porygon2.obj e dal relativo .mtl con texture. La funzione loadModel popola renderablesPorygon2 con buffer di posizioni, normali, texcoords e numVertices per ogni gruppo, pronti per essere passati a renderModel con il programma texture.

10. Interfaccia utente e controlli

HUD (in scena)

  • STARTUP — avvia l'assemblaggio
  • MESH VIEW — modalità wireframe verde
  • SOLID VIEW — modalità solida colorata
  • EVOLUZIONE! — innesca evoluzione → Porygon2, poi commuta in TEXTURE VIEW
  • Dialog box in stile Game Boy con messaggi contestuali

Tastiera

  • 1 · Anim 1 — Saltello
  • 2 · Anim 2 — Posa d'attacco
  • N · Toggle overlay numerazione facce
  • ← → ↑ ↓ · Traslazione camera in XZ
  • Space / Shift · Camera su / giù
  • Mouse drag · Rotazione orbitale (con inerzia)

Il pannello dat.GUI in alto a destra espone Reset camera e le due animazioni di personalità come bottoni di backup ai tasti.

11. Librerie utilizzate

Il progetto utilizza solo librerie consentite dal corso, tutte locali in project/lib/:

  • m4.js — algebra matrici 4×4 column-major (translation, perspective, lookAt, xRotate, …)
  • mesh_utils.js — parsing di file OBJ/MTL e generazione buffer
  • webgl-utils.js — compilazione e linking dei programmi GLSL inline
  • dat.gui.js — pannello di controllo runtime

La telecamera è gestita interamente con eventi nativi del canvas, senza ricorrere a librerie esterne di trackball.

12. Come eseguire

WebGL ha bisogno di essere servito via HTTP per caricare assets, texture e file .obj. Dalla cartella Modulo1/Progetto/project/: 

python3 -m http.server 8080
# poi apri http://localhost:8080/index.html

In alternativa il progetto è accessibile attraverso la hub page del repository o, se hostato su GitHub Pages, all'URL pubblico del repo.
